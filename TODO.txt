-------------------------------------------------------------------------------

[ ] REGERAR O INSTALADOR APOS MOVER O radix-ui
    O pacote radix-ui foi movido de "dependencies" para "devDependencies",
    porque ele so e usado no renderer, que o Vite ja empacota. Estava sendo
    copiado duas vezes e inflando o instalador.
    O instalador atual (96 MB) foi gerado ANTES dessa mudanca.

    Para aplicar:
        1. Fechar o app se estiver aberto (inclusive o icone da bandeja)
        2. Remover a pasta dist/
        3. npm run build:win

    Obs.: se rodar sem fechar o app antes, o build falha com
    "EPERM: operation not permitted, rename dist\win-unpacked.tmp".
    Isso e o Windows segurando os arquivos, nao um bug do projeto.

[ ] ASSINATURA DIGITAL DO INSTALADOR
    O .exe nao e assinado, entao o SmartScreen do Windows exibe aviso na
    primeira execucao. Para resolver e preciso um certificado de assinatura
    de codigo, configurado em win.certificateFile no electron-builder.yml.

[ ] TAMANHO DO BUNDLE DO RENDERER
    O chunk principal esta com ~1.5 MB (aviso do Vite). Nao afeta um app
    desktop (carrega do disco local), mas da para reduzir com code splitting
    por rota se quisermos.

[ ] NORMALIZACAO DE FIM DE LINHA (CRLF/LF)
    O git avisa "LF will be replaced by CRLF" em todo commit. Resolve-se com
    um arquivo .gitattributes definindo "* text=auto eol=lf".
    Cosmetico, nao quebra nada.

[ ] AVISO DO npm SOBRE INSTALL SCRIPTS
    O npm 11 bloqueia scripts de instalacao de alguns pacotes (esbuild,
    electron-winstaller) e exibe aviso. Nada quebrou por causa disso - build,
    typecheck e empacotamento passaram. Se algum dia der problema:
        npm approve-scripts --allow-scripts-pending

6. ANOTACOES TECNICAS (para nao esquecer o motivo)
-------------------------------------------------------------------------------

- BANCO LOCAL usa node:sqlite (embutido no Node 24 do Electron 43), e nao
  better-sqlite3. Motivo: o better-sqlite3 exige node-gyp + Visual Studio
  Build Tools, que nao existem nesta maquina - o npm install falhava.
  Beneficio: nenhuma dependencia nativa, install e build limpos em qualquer PC.

- O PROCESSO PRINCIPAL e CommonJS (o package.json NAO tem "type": "module").
  Motivo: o modulo 'electron' nao expoe named exports quando o main e
  carregado como ESM - "import { app, BrowserWindow } from 'electron'" quebra
  em tempo de execucao.

- A SESSAO usa fs + JSON no lugar do electron-store. Motivo: o electron-store
  v11 e ESM-only e nao carrega no bundle CommonJS do main.

- O SOM DO ALARME e sintetizado pela Web Audio API, nao e um arquivo .mp3.
  Motivo: a CSP bloqueia media-src externo e evita somar peso ao pacote.

- O ALARME roda no processo principal, nao no renderer. Motivo: se rodasse na
  interface, fechar a janela mataria os alarmes.

- A DATABASE_URL nunca sai do processo principal. O renderer roda com
  contextIsolation e so enxerga os canais declarados em src/preload/index.ts.

- MIGRATIONS usam PRISMA, mas o PRISMA CLIENT NAO e usado em runtime. Motivo:
  o client traz um query engine nativo que precisaria ser desempacotado do
  asar no build - a mesma dependencia binaria que evitamos ao sair do
  better-sqlite3. O app continua falando com o Neon via @neondatabase/
  serverless (HTTP) com SQL cru. O Prisma e devDependency.

- No Prisma 7 a connection string NAO fica mais no schema.prisma: vai no
  prisma.config.ts, com um driver adapter. Usamos o adapter pg (TCP) porque
  migration precisa de transacao e advisory lock, que o endpoint HTTP do Neon
  nao oferece.

- O schema.prisma NAO declara foreign keys de proposito. O push do sync envia
  as tabelas em lotes separados, e uma FK rejeitaria uma tarefa cuja categoria
  ainda nao subiu. A ordem correta e garantida por SYNC_TABLES.

- A TRAVA DE REPETICAO FUTURA vive em src/shared/task-rules.ts, e nao em um dos
  processos: o main usa para RECUSAR a operacao e o renderer para DESABILITAR o
  checkbox. Se a regra morasse so num lado, a interface ofereceria uma acao que
  o backend nega.

- OS ICONES DE CATEGORIA sao uma lista curada em src/renderer/src/lib/
  category-icons.ts, e nao o lucide inteiro (1500+): mantem o bundle enxuto e a
  lista navegavel. As CHAVES sao gravadas no banco - nao renomeie uma chave
  existente sem migrar os dados; adicionar novas e sempre seguro.

- O LAYOUT usa CONTAINER QUERIES (@container no AppShell) em vez de breakpoints
  de janela. Motivo: recolher a sidebar devolve ~200px de espaco, e com media
  query normal o conteudo nao reagia a isso.

- AO MUDAR O SCHEMA, alterar em TRES lugares (o app nao usa o Prisma Client,
  entao nada e gerado automaticamente):
      1. prisma/schema.prisma      -> banco remoto
      2. src/main/db/schema.ts     -> DDL do SQLite local + SYNC_COLUMNS
      3. src/shared/types.ts       -> tipos compartilhados
